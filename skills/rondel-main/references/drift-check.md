# 主线检查

检查发生在恢复会话、形成方案、审阅结果、用户改变目标和准备收敛时。先读用户确认的目标、优先数据或条件、当前问题和最近决定，再读本次相关证据。主线检查产生认识和选项，研究者参与路径取舍。

阶段评审和持续缺少实质推进时也触发检查。区分当前缺的是领域覆盖、用户对核心工作的理解、可信复现、机制对照还是收敛表达，并核对用户近期的投入与阻碍。依据 [阶段条件](main-research-loop.md) 和 [状态与推进](main-state-and-momentum.md) 给出一项改变当前局面的行动，记录新的检查点。

| 检查对象 | 需要看见的关系 |
|---|---|
| 问题 | 当前工作怎样回答研究者关心的问题 |
| 优先条件 | 目标数据、任务或应用是否得到实际检验 |
| 机制 | 实际数据流和对照怎样检验候选解释 |
| 证据 | 观察、冻结干预、工程检查和完整训练各支持什么 |
| 协议 | 数据、预算、选点和评价怎样保持可比 |
| 范围 | 下一项工作是否在已确定清单中 |
| 上下文 | 摘要是否忠实于用户修正和原始材料 |

## 具体处理

曾经优先验证的数据条件可以在后续大量实验中被忽略，阶段收益也可能使讨论转向另一个问题。因此，记录中的 priority 与 current_question 同样重要。发现变化时，用一段技术说明指出目前得到了什么、原问题还缺什么，以及保持、开旁支或调整主线分别需要的依据。

用户把贡献重心从成本改回信息组织时，应保留这一修正，后续写作和实验围绕其讨论。对局部结果，先定位实现、融合接线、训练目标与预测行为；反复审计需要说明它将改变哪项决定。工程错误修复在已批准范围内完成，研究路径调整保存人的决定。

## 输出与记录

prepare 阶段准备收束时读 [Pre 退出条件与交互](pre-exit.md)，先反馈整体理解与证据判断，再推荐首轮任务或有限补充。关键阻碍、可带入项与用户当前状态分别保留，退出评审使用 review_type: pre_exit 的 phase_review 记录。实际选择后接续阶段与计划，未完成项继续按原状态跟踪。

产出主线检查笔记，列明用户目标的来源、当前观察、联系或缺口、候选解释和待选择事项。保持“用户确认主线”“AI 解释”“探索旁支”的区别。只有影响判断或下一步时才前置提醒，普通沟通无需机械复述整套检查。
