# Pre 的初始化、核心问题、Todo 与设置版本

正式进入前期时，先恢复 Init 的可检索领域摘要、用户目标与当前计划，再初始化或恢复一份 `purpose: preparation` 的准备总表。每次恢复和阶段复盘按这份总表定位痛点、核心问题、设置与剩余任务；六个前期流程把产物接回同一处。具体执行见 [辅助脚本](preparation-helper.md)，整体路线见 [preparation](preparation.md)。

## 领域摘要、领域痛点与研究问题

领域摘要用一句可检索的名词性表述概括对象、关键设定与常用别名，例如“少样本细粒度的视觉异常检测（VAD/IAD）”。它保存于 `research_anchor.search_summary`，并同步进入画像的 `research_domain`，作为检索的起点；缩写的实际对应在原文中核对。它可以覆盖一个领域，还需要进一步明确当前最值得回答的问题。

领域痛点与核心问题显式保存为 question，通过 purpose 区分 `field_pain` 与 `core_question`。每个痛点记录适用条件、为什么重要、原文或实际观察、已有解决路线、尚缺证据及当前优先级；每个核心问题关联 `pain_refs`，说明要解释或预测什么、目前已知什么、哪种证据会改变判断。可以先维护少量最关键对象，随着阅读合并、补充或暂存，数量随任务决定。

总表 `focus.pain_refs` 和 `focus.question_refs` 保存当前集合，`focus.primary_question_ref` 指向本轮主问题。用户选择的主问题经 observed、clarified 进入 active，来源与理由按原状态规则保留；关联引用也加入总表 refs。AI 提出的局限仍保留候选性质，论文检索、数据选择和复现应明确服务哪个痛点或问题。

## 初始化设置，再按证据确认与冻结

数据、协议、Baseline 与环境分别建立受管理的 resource，purpose 使用 dataset、protocol、baseline、environment。选择讨论与实际设置分开：`baseline_selection` 讨论说明为什么选它，baseline 设置固定真实来源、版本和配方。`setting_key` 表示一个稳定用途，同一项目可以有多个数据集、协议和 Baseline，每个用途独立初始化与版本化。

定义使用 `spec` 映射和正文保存，初始化为 draft。数据清单与内容摘要、类别映射、划分、监督与评价、特征与采样、代码提交和配方、环境锁等需要影响比较的条件写入定义。实际来源核对后资源进入 checked，沿用户对该设置或有限配置清单的真实选择调用 freeze，成为 frozen 的 v1。

冻结后，定义与正文保持不变，实验、运行和相关结论使用 `setting_refs` 固定记录 id、设置版本和定义摘要。资源观测、检查报告与可达性可以单独更新，空闲显存等实时状态仍使用机器资源观测。记录的 revision 表示笔记修订，`setting_version` 表示比较条件的版本，两者分别保存。

不知道采用哪个数据集时，总表先显示 todo，并按需要保留候选草案；不能把空白或未核验项标为完成。已有普通资源卡可以继续读取，纳入受管理设置前核对并创建关联的设置版本，旧记录保留。旧实验缺少依赖引用时会注明无法自动判定影响，需要人工补充核对；旧工具名 `pre.benchmarks` 只作为 context 兼容别名，新流程统一使用 `pre.baseline`。

## 修改设置：新版本、影响清单和处理方式

修改冻结定义时先说明原因，调用 revise 从当前冻结版本建立 v2 草案。旧版本与旧结果原样保留，草案重新核验并确认冻结后成为该用途的当前版本；现有实验不会被自动改绑。更高版本已经存在时先处理它，避免同一用途出现未说明的版本分叉；并行的不同研究设定使用不同 setting_key。

每次初始化、定义草案修订、冻结和版本变更都会进入现有历史事件，记录时间、来源、理由、版本、变化字段与潜在影响。影响追踪沿 `refs`、`project:` 引用和 `setting_refs` 连接方案、运行、分析及主张，结果是需要审阅的对象清单。处理说明区分保留、复核、重算或移出当前比较，证据不足时保留待定，引用关系本身不判定旧结论无效。

例如修正标注会要求核对旧评价与相关结论；只迁移存储而内容摘要相同时，可以说明依据后保留对应结果。`impact_review.summary` 保存总体判断，`impact_review.results` 按记录引用保存 action 和 reason，`keep` 需要具体理由。确认新版时，仍引用旧设置的 Todo 会提示 needs_review；已审阅且有保留依据的对象可保持完成，实际旧运行仍绑定原版本。

## Todo 怎样判断前期是否完成

| 跟踪项 | 完成时应有的依据 | 后续把关 |
|---|---|---|
| 领域痛点 | 有来源与条件的当前痛点集合 | 新材料是否改变重要性或证据状态 |
| 核心问题 | 与痛点关联、主问题明确且已选择 | 当前工作是否回答这个问题 |
| 领域阅读 | 主要路线地图与核心集合 | 是否需要补一条路线，或应当收拢 |
| 核心理解 | 用户自己的摘要、解释与疑问 | AI 代读与用户实际理解分别记录 |
| 数据设置 | 本轮选定数据的核验与冻结版本 | 内容、标签、划分或特征是否变化 |
| 协议设置 | 输入、监督、选点与评价的冻结版本 | 新结果是否真正按同一条件比较 |
| Baseline 设置 | 来源、提交、配方和差异明确 | 是否忠实复用、是否发生核心改变 |
| 环境设置 | 目标机器与经过核验的环境定义 | 依赖、数值条件与入口是否变化 |
| 基线复现 | 约定范围的有效运行与复现核对 | 工程跑通和可信复现分别说明 |
| 阶段复盘 | 完成依据、关键缺口和首项中期验证 | 沿实际用户选择决定进入下一阶段 |

任务状态使用 todo、in_progress、blocked、done；不适用时可沿真实用户来源标为 waived 并说明原因。done 需要实际证据引用，脚本会核对引用存在、角色和版本，依据变化时显示有效状态 needs_review。设置变化后的结果、复现与阶段审阅也沿依赖检查，不能只重新勾选一个完成框。

`status` 只读给出清单、当前版本与缺口，`checklist_complete` 只表示这些结构检查通过。实际理解、复现可信度、问题价值与科学可比性仍由 Main 结合原始材料共同审阅。Main 到评审点提出转阶段或有界补充建议，不因勾选或时间经过自动晋级。

`pre_review_tasks_complete` 排除 phase_review 本身，标明常规准备项的结构状态；它与包含复盘项的 checklist_complete 分开。发起评审不必等到全部勾选，具体退出标准、阻碍与可带入项见 [Pre 退出](pre-exit.md)。带入中期的未完成工作保留真实状态及后续任务，不能当作已完成或不适用项。

## 文件与持续把关

总表是正常的 discussion 记录；可读 Todo 和 Changelog 由明确的 report 操作重建，分别位于 `.rondel/setup/preparation-todo.md` 与 `.rondel/history/preparation-changelog.md`。它们是展示投影，来源仍是总表、设置记录和历史事件，生成区外的研究者讨论保留在总表。无需在工作区根目录建立新的分类目录。

Main 每轮围绕本轮相关项检查：当前问题、正在使用的设置版本、与原计划的偏差、新证据和用户未完成的判断。发现定义变化先定位受影响比较，机械故障修复沿已有范围继续；改变数据、监督、模型或评价条件则进入版本与影响审阅。预备清单负责守住研究起点，探索仍可以带着明确的未知项前进。
